## Remaining algorithmic and real-world limits

The [50,000-ad benchmark](validation/scale-50000.json) ran on macOS arm64/Node 26.7.0 at one fixed evaluation clock. It compared full, compact, decoded-browser and paginated API-core results plus ad-level alert baselines across 16 searches. The run took 59.88 seconds, compared 22,500 indexed candidate pairs instead of the 1,249,975,000 all-pairs upper bound, and produced 86,765,445 packed bytes versus 223,817,309 full bytes. Its maximum sampled resident memory was about **2.00 GB**. Those figures describe the synthetic fixture and host, not a universal performance promise.

- API reads are bounded to 500 database rows, but the core retains all matches for sorting/grouping and rescans candidates for each page request. Memory remains O(matches); late offset pages can be expensive. The benchmark uses the actual API core with serialized in-memory batches, **not real SQLite disk, HTTP or browser-render throughput**.
- Candidate blocking avoids generic-title explosions, but a dense identifier/stock/distinctive-title bucket can still require quadratic pair work. The distributed fixture is not a worst-case bound. Silent candidate truncation would violate review reachability.
- A shared sort comparator plus a tested top-K/group-aware selection algorithm can reduce retention. A result-ID cache keyed by data revision, filters, workspace and evaluation clock can avoid repeated scans. A naive ad-level cursor before group representative selection can repeat a crosspost and must not be substituted without parity tests.
- Better candidate ranking does not prove that the original 1,576 ads are 1,576 unique vehicles. Most original ads still lack strong documentary identifiers, full detail enrichment and human cross-list review. Photo similarity was not added without appropriate image rights.

## External barriers remain explicit

Access handling is improved; access itself is not manufactured. The last observed 500 Classic 403/challenge-associated pagination, Autotrader unavailable pages/storage restrictions, permission-restricted marketplaces/forums, JWS detail failure and other gaps remain described in [SOURCE_COVERAGE.md](../SOURCE_COVERAGE.md) and the dated source research. No denied source is interpreted as zero inventory, and no challenge, login or proxy bypass was introduced.

Remaining external acceptance work requires the relevant input: authorized ORS credentials and representative routes; an opted-in SMTP/webhook destination; approved dealer/auction/provider exports or licensed API access; Windows launcher/autostart acceptance; and browser connectivity from the deployed HTTPS site to the private backend. Disabled sources cannot be enabled merely by recording an operational review. Existing source data and private notes remain separate from synthetic fixtures and test databases.
