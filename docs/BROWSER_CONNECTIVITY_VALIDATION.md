# Native browser context validation

Observed September 8, 2026 UTC against local MuscleScout at `http://127.0.0.1:3100/`, using isolated Playwright Chromium **153.0.8010.12** profiles. No existing user profile, workspace cookies, external images, seller pages or service credentials were used. No polyfill or replacement WebMCP implementation was injected.

Without the development feature flag, localhost was a secure context and `document.modelContext` was absent. With `--enable-features=WebMCP`, the browser exposed native `registerTool`, `getTools` and `executeTool`. This is Chromium's actual development flag, mapped from its `enable-webmcp-testing` UI flag. [Chrome's WebMCP development guidance](https://developer.chrome.com/docs/ai/webmcp?hl=en), [Chromium flag definition](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/chrome/browser/about_flags.cc)

The real app registered exactly one `search_musclescout` tool after hydration. A native invocation applied `Camero` to the visible search, invalid mode input was rejected and reload left one registration. Native diagnostic tools confirmed that registration returns a Promise, aborting the registration signal removes the tool, cancellation reaches the execution callback's AbortSignal, the caller receives AbortError and cleanup leaves no diagnostic registrations.

The installed Chromium's actual API differs from the current draft: `executeTool` takes JSON text as its second argument, while the newer draft accepts an object. Object invocation returned `UnknownError: Failed to parse input arguments`; the documented native JSON-string signature succeeded. The app's registration/execute callback requires no polyfill for this difference. The diagnostic records both outcomes and the used input format. [Exact Chromium 153 IDL](https://chromium.googlesource.com/chromium/src/+/153.0.8010.12/third_party/blink/renderer/core/script_tools/model_context.idl), [current WebMCP draft](https://webmachinelearning.github.io/webmcp/)

A separate native check verified that invoking only query/mode preserves an already selected maximum price. The first run exposed Zod optional/default behavior resetting omitted filters; the callback now uses a strict optional patch without defaults. The final check at 16:35:02Z returned exactly `{"applied":{"query":"Camero","mode":"unknown-route"}}` and preserved the existing maximum price of 45000. No page errors occurred.

Run `node scripts/diagnose-browser-context.mjs` with the local web server running. An optional `--url=` HTTPS target additionally requires `--authorized-https=true` and a user-supplied authorized destination. No such destination has been supplied or tested. Local development success does not establish an origin trial, real Pages publication, an actual browser agent's internal discovery UI or HTTPS-to-private-backend permission behavior.
